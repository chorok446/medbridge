# 근거 우선 답변 화면 설계 (Evidence-first QA)

- 작성일: 2026-08-04
- 상태: 승인됨 (구현 계획 대기)
- 레퍼런스: [Vera Health](https://www.verahealth.ai/), OpenEvidence

## 1. 배경

두 레퍼런스는 임상 의사결정 지원 제품이지만, 이 설계가 가져오는 것은 **제품 성격이 아니라 화면 패턴**이다. 그들이 실제로 잘하는 것은 네 가지다.

1. 답변 문장 **안에** 인용 번호가 박혀 있다 — 문장과 근거가 붙어 있다.
2. 근거가 부족하면 답을 만들지 않고 그렇다고 말한다.
3. 후속 질문을 제안한다.
4. 질문을 크게 받는 검색 화면으로 시작한다.

MedBridge는 2번을 이미 지킨다(`insufficient_evidence` / `not_found`). 3번은 **모델이 만들고 서버가 받아놓고는 버린다** — `verify()`가 `followups`를 채워 `_finalize()`까지 넘기지만(`service.py:479`), `_finalize()`가 하는 일은 `if followups: assistant_msg.error_code = None`뿐이고(`service.py:501-502`) `QaMessage`에 저장할 컬럼이 없다. 1번과 4번은 아예 없다.

### 1.1 진짜 문제 — 읽는 문장과 검증된 문장이 다르다

`answer`와 `claims`는 서로 독립적인 모델 출력이다(`apps/api/app/services/qa/schema.py:210,216`). 검증(유효 출처·수치 존재·어휘 접지)은 `claims`에만 걸리고, `answer` 산문은 검증 없이 그대로 저장된다.

현재 화면은 그 **검증되지 않은 산문을 본문으로 크게 보여주고**, 검증된 주장은 그 아래 작은 회색 글씨로 붙인다(`apps/web/components/document-qa.tsx:337-347`). 사용자가 실제로 읽는 문장이 근거가 확인된 문장이 아니다.

인라인 인용은 미관 개선이 아니라 이 구멍을 메우는 일이다.

## 2. 목표 / 비목표

### 목표

- 답변 본문에서 문장 단위로 근거를 짚을 수 있다.
- 화면에 보이는 인용 번호는 **전부** 검증을 통과한 근거만 가리킨다.
- 백엔드가 이미 만드는 후속 질문을 사용자가 본다.
- 문서를 열면 "무엇을 물어볼까"가 먼저 보인다.
- 읽는 글이 실제로 읽기 좋다(17px / 행간 1.7).

### 비목표 (이번 범위에서 만들지 않는다)

- **DDx(감별진단) · Tx Plan(치료계획) · Clinical Calcs.** `PRODUCT.md:17`의 "진단·처방·응급 판단 기능은 영구적으로 만들지 않는다"에 정면으로 걸린다. Vera의 간판 기능이지만 이 제품에는 들어오지 않는다.
- 음성 질문(OpenEvidence의 hands-free). 로컬 STT가 별도 과제다.
- 문서 목록 화면의 전역 질문창. 백엔드가 문서별 QA만 지원한다.

**마이그레이션은 후속 질문 저장 한 건만 한다.** 인용 마커는 기존 `content` 안에 들어가므로 스키마를 건드리지 않는다. 후속 질문은 저장할 곳이 없어 컬럼이 하나 필요하다(§4.3).

## 3. 인용 계약 (백엔드)

### 3.1 마커 문법

모델이 `answer` 산문 안에 `[c<n>]` 형태의 마커를 넣는다. `<n>`은 같은 응답의 `claims` 배열 인덱스(0-based)다.

```
심부전 환자의 나트륨 제한은 하루 2g 이하를 권장한다[c0]. 다만 중증 환자에서는
과도한 제한이 오히려 예후를 악화시킬 수 있다[c1][c2].
```

파싱 정규식은 `\[c(\d{1,2})\]`로 고정한다. `MAX_CLAIMS = 20`이므로 두 자리면 충분하고, 문서 본문에 나올 수 있는 일반 대괄호(`[1]`, `[표 3]`)와 충돌하지 않는다.

### 3.2 `verify()` 규칙

`apps/api/app/services/qa/schema.py`의 `verify()`에 마커 검사를 추가한다.

1. `answer`에서 마커를 전부 찾는다.
2. 다음 중 하나라도 해당하면 **그 마커를 본문에서 제거한다** (주변 텍스트는 남긴다):
   - 인덱스가 `claims` 범위 밖
   - 가리키는 claim의 `verification_status`가 `unsupported`
   - `not_found` / `insufficient_evidence`로 확정되어 claim이 비워진 경우
3. 제거는 조용히 하지 않는다 — 제거 개수를 구조화 로그로 남긴다(원문은 남기지 않는다). 마커가 통째로 사라지는 회귀를 로그에서 볼 수 있어야 한다.
4. 마커 검사는 claim 검증이 **끝난 뒤**에 돈다. `conflicting_evidence`로 승격되며 상태가 바뀐 claim은 유효한 인용 대상으로 남는다.

`answer`는 마커를 포함한 채로 `ANSWER_MAX_CHARS = 4000` 제한을 받는다. 마커 제거는 길이를 줄이기만 하므로 재절단은 필요 없다.

### 3.3 폴백 — 마이그레이션이 필요 없는 이유

마커가 하나도 남지 않으면(모델이 안 넣었거나 전부 무효) 프론트는 **현행 렌더**로 돌아간다: 산문 본문 + 그 아래 claim 목록.

기존에 저장된 메시지에는 마커가 없으므로 자동으로 이 경로를 탄다. 새 컬럼도, 백필도 없다.

### 3.4 스트리밍은 바꾸지 않는다

현재 스트림은 `claim` 이벤트만 보내고 최종 본문은 `completed` 이벤트에 실려 온다(`apps/web/types/qa.ts:67-75`). 그대로 둔다.

- 진행 중: 지금처럼 claim이 도착하는 대로 목록으로 보여준다(진행 표시 역할).
- 완료 시: 마커가 박힌 본문으로 교체된다.

프로토콜 변경 없음.

### 3.5 프롬프트

`apps/api/app/services/qa/provider.py`의 지시문에 마커 규칙을 추가한다.

- 확정 사실을 서술한 문장 끝에 그 근거 claim의 `[c<n>]`을 붙인다.
- 근거가 없는 문장에는 마커를 붙이지 않는다.
- 마커는 `claims` 배열에 실제로 넣은 항목만 가리킨다.

모델이 규칙을 어겨도 3.2가 화면을 지킨다. 프롬프트는 품질을 올리고, 검증이 안전을 책임진다.

## 4. 프론트 렌더

### 4.1 인용 pill

`content`를 마커 기준으로 토큰화해 `텍스트 | 인용` 시퀀스로 만든다. 이 토큰화 함수는 순수 함수로 분리해 단위 테스트한다.

인용 pill을 누르면 해당 claim의 첫 `sourceRef`로 PDF가 이동하고 하이라이트가 번쩍인다 — 지금 `SourceBadges`가 하는 동작 그대로다. pill은 `<button>`이고 접근성 라벨은 "3쪽 근거 보기" 형태로 준다.

### 4.2 출처 섹션

본문 아래에 번호순 출처 목록을 둔다. 각 항목은 쪽수 · 섹션 제목(`sectionTitle`) · 출처 방식(`digital` / `ocr`)을 보여준다.

`sourceMethod`가 `ocr`인 항목은 "스캔 인식"으로 표기한다. 사용자가 그 근거를 얼마나 믿을지 판단할 수 있어야 한다. 기술 용어(OCR, bbox, blockId)는 화면에 내지 않는다 — `PRODUCT.md`의 anti-reference.

### 4.3 후속 질문

모델이 만든 후속 질문을 답변 아래 칩 3개로 렌더한다. 누르면 입력창에 들어가는 것이 아니라 **바로 전송된다** — 한 번 더 누르게 만들 이유가 없다.

저장 경로가 없으므로 만든다.

- 마이그레이션 `0012`: `qa_messages.followups_json` (JSON, nullable)
- `_finalize()`가 실제로 저장한다. 현재의 `if followups: assistant_msg.error_code = None`은 후속 질문과 아무 상관이 없는 줄이므로 함께 걷어낸다.
- `MessageOut.followups`로 응답에 노출, `QaMessage` 타입에 `followups: string[]` 추가

기존 메시지는 `null` → 빈 배열로 읽어 칩을 렌더하지 않는다. 백필 없음.

## 5. 질문 탭 IA

### 5.1 기본 탭

추출이 끝난 문서(`hasExtraction`)는 기본 탭이 **질문**이다. 처리 중이거나 추출 실패면 기존대로 **문서 보기**. 탭 4개 구조 자체는 유지한다.

### 5.2 빈 상태 = 검색 화면

대화가 없을 때 질문 탭은 채팅창이 아니라 검색 화면이다.

- 중앙에 큰 질문 입력창
- 아래 예시 질문 3개 (카드)
- 위에 학습 모드 칩 3개

### 5.3 대화가 시작된 뒤

말풍선을 버린다. 질문은 파란 말풍선이 아니라 **제목**(18px semibold), 답변은 **본문**(17px / 행간 1.7)이다. 두 레퍼런스가 공통으로 하는 일이 "대화가 아니라 문서로 보이게 만드는 것"이고, `DESIGN.md`의 야간 가독 규칙(17px+ / 1.7)이 여기서 처음 지켜진다 — 현재 답변 본문은 14px다.

## 6. 학습 모드 (LearnerLevel)

Vera의 모드 탭 자리에 기존 `LearnerLevel`(`concise` / `nursing_student` / `experienced_nurse`)을 올린다. 새 임상 표면을 만들지 않고 모드 감각만 얻는다.

**주의: 공짜가 아니다.** `learner_level`은 현재 요약 파이프라인에만 존재하고 QA 경로에는 없다. 다음이 필요하다.

- QA 요청 스키마에 `learnerLevel` 추가 (선택 필드, 기본 `nursing_student`)
- `qa/provider.py` 프롬프트에 수준별 지시 반영
- 스트림 요청 경로(`stream_service.py`)로 값 전달

**저장하지 않는다.** 값은 요청마다 보내고 마지막 선택만 브라우저에 기억한다. 스레드·메시지에 저장하면 마이그레이션이 생기는데, 이 기능이 그 값을 치를 만큼 중요하지 않다. 재시도(`retryAnswer`)는 현재 UI 선택값을 쓴다.

## 7. 요약 탭

`SummaryArtifact.sourceRefs`가 이미 있으므로 질문 탭과 **같은 인용 pill·출처 섹션 컴포넌트를 공유**한다.

요약의 모델 계약은 바꾸지 않는다. 아티팩트 단위 출처를 pill로 통일하는 선까지만 하고, 요약 본문 안 인라인 마커는 이번 범위가 아니다.

## 10. 검증

### 백엔드 단위 테스트 (`tests/unit/test_qa_schema.py`)

- 해석 불가 마커(범위 밖 인덱스)가 본문에서 제거된다
- `unsupported` claim을 가리키는 마커가 제거된다
- 마커가 0개면 `answer`가 그대로 남는다 (폴백 경로)
- 같은 claim을 가리키는 중복 마커가 모두 유지된다
- `conflicting`으로 승격된 claim의 마커가 살아남는다
- `insufficient_evidence` 확정 시 마커가 전부 제거된다

### 프론트 단위 테스트

- 토큰화 함수: 마커 있음 / 없음 / 연속 마커(`[c0][c1]`) / 잘린 마커(`[c`)
- 마커 없는 기존 메시지가 현행 렌더로 떨어지는 회귀 테스트

### 통합

- QA 스트리밍 완료 후 최종 메시지에 마커가 보존되는지
- `learnerLevel`이 프롬프트 경로까지 전달되는지

## 12. 리스크

- **모델이 마커를 잘 안 넣는다.** 로컬 소형 모델은 지시를 흘릴 수 있다. 폴백이 있으므로 화면은 깨지지 않지만, 폴백만 계속 타면 이 설계의 절반이 죽는다. 제거·미삽입 비율을 로그로 관찰하고, 낮으면 프롬프트를 조정한다.
- **`document-qa.tsx` 재구성 범위.** 405줄 단일 컴포넌트를 건드리므로 스트리밍·취소·재시도 회귀 위험이 있다. 인용 렌더를 먼저 분리하고, 그다음 IA를 바꾸는 순서로 나눈다.
