# Q&A 상태 대상 해석 후보 비교 — 2026-09-17

## 원인 분리와 비교 계약

이전 확장 평가의 `new_subject_axes`에서 구동 방식은 선택되지만 점검 상태가 빠졌다.
선택기/정답표를 변경하지 않은 단독 진단을 현재 Ollama 0.34.1에서 수행했다.
모델 출력은 원문이 아닌 스키마 검증을 통과한 범주 값만 관찰했다.

| 묶음 | 실제 내용 역할 | 모델 target | 모델 basis |
|---|---|---|---|
| 0 | 다른 실체의 재질 | other | none |
| 1 | 질문 대상의 구동 방식, 출처 1·2 | same | type |
| 2 | 질문 대상의 점검 상태, 출처 3 | **other** | stage |

모델은 상태를 stage로 구분했지만 그 상태를 갖는 실체가 질문 대상과 같다는 점을 놓쳤다.
파서가 반환값을 잘못 읽거나 입력 원문/출처를 잃은 문제가 아니었다. 입력과 모델 digest는 유지됐고,
기존 채점기가 누락 1개·불완전 기준 1개를 검출했다. 단독 진단은 전체 게이트가 아니며 종료 2다.

새 `entity_checklist`는 기존 `fact_checklist`의 지침에 **실체와 그 속성·상태의 관계**를 명확히
설명하는 부분만 덧붙인다. 다른 실체나 원문 명령의 단어 일치만으로 same을 부여하지 않고,
질문이 특정 기준만 요구하면 다른 기준은 계속 제외한다. 사례의 명칭·출처 위치·정답은 넣지 않는다.

- 기본 후보 baseline과 이전 후보 3개를 유지한다. 앱/최종 답변에는 연결하지 않는다.
- 질문·이력·원문·그룹·모델·옵션·출력 스키마·엄격 파서·취소/기한은 동일하다.
- other/stage를 코드에서 same으로 강제 교정하지 않는다. 같은 오판정이 오면 새 후보도 실패한다.
- 기존 fixed/extended 입력·기대값·전체 반복·미완료/오류 차단 계약은 그대로다.
- 이번 지침 보강에 사용한 기존 8사례는 **개발용 회귀 자료**다. 독립 검증 자료라고 주장하지 않는다.
  통과하더라도 별도의 새로운 검증 자료와 실제 문서/최종 답변 평가가 필요하다.

## 모델 호출 전 고정한 실행 계획

단독 진단 1회와 별도로, 같은 0.34.1 환경에서 기존 `fact_checklist`와 새 `entity_checklist`를
각각 `extended` 전체 8사례×3회로 평가한다. 단일 호출 60초·전체 600초·동일 모델 digest 검사를
유지하며, 실행 오류는 그 실행을 즉시 중단한다. 품질 실패는 반복별로 모두 기록한다.
두 후보의 부분 성공을 합치거나 통과할 때까지 재시도하지 않는다. 결과를 보고 지침/기대값을 바꾸지 않는다.

작업 시작 시 이미 Ollama **0.34.1**이 실행 중이었다. 지난 0.34.0 기록과는 런타임이 다르며,
이번 작업에서 업데이트·설치·재시작하지 않았다. 이전 오류가 버전 업데이트로 해결됐다고 단정하지 않는다.
직전 HEAD `b42d65d`의 CI **34921891931 전체 6개 작업 success**를 확인했다.

`apps/api`에서:

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_source_selection.py --local --strategy fact_checklist --suite extended
exit $LASTEXITCODE
```

새 후보는 별도 실행에서 `--strategy entity_checklist`를 사용한다. 사용자 DB/문서는 필요하지 않다.

## 실행 환경과 통신 오류의 한계

- 두 평가 전후 Ollama 버전은 0.34.1이었다. 모델은 같은 `qwen3:8b`이며 설치/적재 digest는
  `sha256:500a1f067a9f782620b40bee6f7b0c89e17ae61f686b92c24933e4ca4b2b8b41`로 유지됐다.
- 검사 시 모델은 6,295,440,588바이트 전부 VRAM에 적재, context 8192였다.
  오류 뒤에도 앱 PID 3232, 서버 PID 5428, 자식 실행 PID 30940이 존재했다.
- 서버는 오류 요청 시각 **00:07:39 KST**에 HTTP 200을 기록했지만 클라이언트는 연결 오류를 받았다.
  서버의 200만으로 클라이언트 수신 성공을 판단하지 않는다. 이번에는 원래 예외의 WinError 번호를
  수집하지 않았으므로 이를 과거 WinError 10054와 동일 사건/원인이라고 단정하지 않는다.
- 검사한 서버 로그 tail에서 panic/OOM 패턴은 없었다. 이것만으로 시스템·드라이버·전송 문제를

- 이번 작업에서는 Ollama/드라이버/모델 설치·업데이트·재시작·삭제·환경 설정 변경을 하지 않았다.
