## 재현한 원인과 최소 수정

이전 `3dd178b` 평가의 프롬프트 주입 사례 claim 0 실패를 조사했다.
같은 제품 코드인 `037713f`에서 합성 사례만 추적했으며 사용자 자료는 사용하지 않았다.
추적은 임시 DB 환경 설정 후 기존 평가기의 검색·공급자·검증·저장 경로를 감싸고,
파싱 전 content와 native done 프레임을 해당 합성 사례에서만 수집했다.
원문 수집은 시도당 8,192자로 제한했고 키·사용자 문서·프롬프트 본문은 수집하지 않았다.

- 단독 12회는 모두 completed였으나 5회는 마지막 final JSON의 괄호가 손상돼 있었다.
  앞줄의 정상 claim은 남아 claim 0 실패가 아니었다. 괄호를 보충하는 수정은 하지 않았다.
- 전체 순서 39회에서는 첫 프롬프트 주입 사례(전체 34번째)가 같은 claim 0으로 실패했다.
  모델 출력은 **완전한 claim 객체와 완전한 final 객체가 줄바꿈 없이 붙은 223자**였다.
  native done 1회, 파싱 이벤트 0, invalid line 1이다. `json.loads`가 `Extra data`로
  두 객체를 함께 버리는 원인을 확인했다. 전체는 38/39, 평가기 반환 코드 2였다.
- `a9d945e75821cc213f71d967f2b6cc789c8328d1`은 `JSONDecoder.raw_decode`로
  한 줄의 완전한 claim/final 객체를 순서대로 읽는다. JSON 문법은 수리하지 않는다.
  한 줄에 자유 텍스트·미상 이벤트·배열·잘린 꼬리가 있으면 그 줄 전체를 거부한다.
  문자열 내부의 괄호·인용부호는 객체 경계로 취급하지 않는다.
- 한 줄 최대 21개 객체(기존 claim 상한 20개 + final), 전체 claim 상한과 final 종료를
  유지한다. 마지막 줄에도 claim 누적 상한을 적용한다. native Ollama/OpenAI 양쪽을 검증했다.
  출처·수치·어휘·극성 검증, 모델 프롬프트·설정·데이터셋·평가 게이트는 변경하지 않았다.
- 실제 수집한 실패 응답을 그대로 재생하면 기존 파서는 `Extra data`, 수정 후에는
  claim/final 2개와 지원 claim 1개다. 원래 claim 본문·ID가 그대로이며 거부 사유는 없다.
  원시 응답 SHA-256: `856d8b6a92742bd378f74a3860ddf077cc755f898b929e9136051462ec8521ab`.
  공개 JSON의 합성 UUID는 일관된 별칭으로 바꿨다. 이 해시는 별칭 치환 전 응답 기준이다.
