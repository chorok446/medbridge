## 변경 이유와 계약

앞선 출처 고정 재서술 시험에서는 원문 등급을 다른 숫자 표기로 바꾸는 문제가 남았다.
이번에는 모델의 표기 보존 지침을 더 추가하지 않고 생성 자체가 없는 구조화를 시험한다.
기존 숫자·어휘·부정 검사는 수정하지 않으며 재서술 결과를 검증된 답변으로 승격하지 않는다.

- 입력은 현재 문서에서 검색된 완전한 청크와 출처 lookup이다. 최대 32개·전체 12,000자,
  청크당 3,000자 상한을 유지하며 빈 본문·중복 ID·출처 불일치·잘린 입력은 전체 거부한다.
- 빈 줄 뒤 문단 시작에 같은 계열의 표지가 연속으로 증가할 때만 항목을 나눈다.
  Roman·Unicode Roman·영문·일부 숫자 목록을 인식한다. 누락·역순·중복·혼합 또는
  불명확한 구조는 청크 전체 원문 한 항목으로 보존한다. 단위가 붙은 일반 수치는 나누지 않는다.
- 표지 인식에만 정규화를 사용한다. 반환 텍스트는 저장 청크의 정확한 문자 범위를 복사한다.
  머리말·중간 조건·예외·뒤 문맥·공백을 삭제하지 않으며 항목을 다시 이으면 입력과 일치한다.
- 모든 검색 청크를 입력 순서 그대로 반환한다. 같은 본문이어도 다른 출처를 합치거나 제거하지
  않으며 숨은 lookup 자료를 선택하지 않는다. 원문·해시·출처 좌표는 독립 복사한다.
- 항목은 문자 구간일 뿐 의미상 등급/조건의 관계를 확인한 결과가 아니다. 마지막 항목에 붙은
  뒤 문맥을 그 등급에만 적용되는 조건이라고 주장하지 않는다. 쪽수·bbox는 청크 전체 출처다.
- 문자 위치는 Python Unicode 코드 포인트 인덱스다. 바이트나 브라우저 UTF-16 위치가 아니다.
  앱에서 개별 항목을 강조하려면 별도 위치 변환과 블록 대응 검증이 필요하다.
- 모델 호출·관련 구간 선택·DB 쓰기·앱 라우트 연결은 없다. 문서 소속 확인은 호출자가 맡는다.
  제품의 동의·revision·취소·대화 저장 절차나 최종 답변 계약을 대체하지 않는다.

원문 보존은 **저장된 검색 청크 텍스트**를 기준으로 한다. PDF 파일의 바이너리 보존이나
추출/OCR 정확성을 새로 입증한 것이 아니다. 잘린 검색 입력을 감지하면 자동 복구하지 않는다.

## 자동 검증과 셀프 리뷰

- 새 단위 45개·합성 PDF 통합 1개: **46 passed**, 1.49초.
- 전체 API **1,690 passed / 4 skipped**, 160.68초. Ruff·mypy 133개 소스 통과다.
  기존 Starlette/httpx 경고 1건과 접근 불가 캐시 폴더는 그대로 두었다. 검사 완화는 없다.
- Roman → Arabic 변환이 기존 숫자 검사에서 거부되는 합성 사례를 먼저 재현하고,
  같은 자료를 원래 표기로 복사하는지 확인했다. 안전 검사를 완화하지 않았다.
- LF/CRLF·들여쓰기·구분자·결합문자·이모지·긴 조건·중복 출처·출처 불일치·입력 상한·
  불완전 목록·일반 수치·명령처럼 보이는 원문을 검사했다. 입력 스냅샷도 보존한다.
- 합성 PDF를 실제 업로드·추출·검색한 뒤 네 등급과 조건이 각각 같은 행으로 남는지 검사한다.
  DB 새 세션에서 원문·해시·좌표가 같고 Q&A 답변이 저장되지 않았음을 확인했다.
- 셀프 리뷰: 제품 서비스/라우트 미연결, 원문 절단/필터링 없음, 항목별 좌표를 생성하지 않음,
  추출 구조와 의미 검증의 구분을 확인했다. 기능과 무관한 파일 정리·서식 변경은 하지 않았다.
