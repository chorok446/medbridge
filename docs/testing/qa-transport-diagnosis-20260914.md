# 로컬 연결 진단과 재시작 후 게이트 — 2026-09-14

평가 코드 `4c20e16`, 제품 `9cc6414` 변경 없음. 고정 사례·정답표·채점·60초 제한도 그대로다.
최종 **일반 모드에서 3사례×3회 모두 통과, 종료 코드 0**을 확인했다.
다만 기존 간헐 연결 재설정의 근본 원인은 미확정이다. **제품 적용·릴리스 승인 아님, Draft·HOLD 유지.**

## 연결 경로 비교 — 추측으로 취소 가드를 제거하지 않는다

비의료 합성 자료만 사용해 총 54회 계측했다. 모델 본문 대신 사례 ID·시각·단계·상태 코드·
OS 오류 번호를 기록했다. 각 요청은 새 연결이며 모델 digest와 입력 보존도 확인했다.

| 진단 | 경로 | 시도 | 연결 재설정 / HTTP 500 |
|---|---|---:|---:|
| 최초 비교 | 기존 취소 지원 연결 | 9 | 3 / 0 |
| 최초 비교 | 표준 HTTPConnection | 9 | 0 / 0 |
| 생성/콜백 분리 | 기존 취소 지원 연결 | 6 | 1 / 0 |
| 생성/콜백 분리 | 표준 socket.create_connection만 대입 | 6 | 1 / 0 |
| 생성/콜백 분리 | 연결 직후 헤더 취소 콜백 해제 | 6 | 1 / 1 |
| 중단 계측 | 기존 취소 지원 연결 | 9 | 1 / 0 |
| 중단 계측 | 표준 HTTPConnection | 9 | 0 / 0 |

- 54회 중 46회는 결과가 반환되어 고정 기대값과 일치했다. **WinError 10054 7회와 HTTP 500
  1회**를 보존했다. 진단 행렬은 오류를 기록하면서 예정된 비교만 마치며, 종료 0은 계측 완료일
  뿐 게이트 통과가 아니다. 실제 고정 게이트 실행은 아래처럼 별도로 기록했다.
- 실패한 TCP 연결도 먼저 `127.0.0.1:11434` 연결을 완료했다. 이후 HTTP 응답 헤더 수신 단계에서
  재설정됐다. DNS 실패나 입력/출력 JSON 검증 오류로 바꾸어 기록하지 않았다.
- 첫 비교만으로 취소 지원 코드가 원인이라고 단정할 수 없다. 표준 소켓 생성과 조기 콜백 해제
  경로에서도 실패했다. 완전한 표준 연결의 관찰 성공 18회 역시 간헐 오류 부재를 보장하지 않는다.
- 중단 계측 18회에서는 `socket_abort`와 `deadline_expired` 호출이 없었다. 오류 시 `close`가
  관찰되지만 Python 표준 `getresponse`는 `response.begin()`의 ConnectionError를 받은 뒤에도
  close를 호출한다. 이 기록을 클라이언트가 먼저 강제 종료했다는 증거로 취급하지 않았다.
- 비교 대조군은 진단 프로세스 안에서만 연결 클래스를 교체했다. 표준 생성/조기 콜백 해제는
  일부 취소 보장이 없으므로 제품 대안으로 채택하지 않는다. 앱의 HTTP 코드는 변경하지 않았다.
- 서버 로그의 고정 오류 패턴 검사만으로 재설정 원인을 찾지 못했다. 전체 프로세스 재시작 전에
  상세 로그 수집의 필요성과 다른 요청 중단 가능성을 설명하고 사용자 승인을 받았다.

## 승인된 재시작과 복구 — 작업 중 발생한 문제도 보존

기존 설치된 Ollama 0.34.0을 사용했다. 새 설치·모델 다운로드·드라이버 변경은 없다.
상세 로그는 자식 프로세스에만 `OLLAMA_DEBUG=1`을 전달했고, 사용자/시스템 환경 설정은 변경하지 않았다.

|---|---|---:|---|
| 상세 로그 재시작 후 | 9회 기대값 일치 | 9 | 완료·통과 / 0 |
| 일반 모드 복구 직후 | 첫 요청 60.014초 시간 초과 | 1 | 미완료·실패 / 2 |

일반 모드 복구 후의 두 시간 초과는 앞선 연결 재설정과 구분해야 한다.
**에이전트가 재시작 시 부모 앱/서버만 종료하고 자식 실행 프로세스의 종료를 확인하지 않은
절차상 실수**가 있었다. 다음 두 이전 프로세스가 현재 실행 프로세스와 함께 남아 있었다.

- 이전 서버 PID 25400의 `llama-server.exe` PID 15252.
- 상세 로그 서버 PID 12692의 `llama-server.exe` PID 31900.

두 부모가 종료됐고 실행 파일이 해당 Ollama 설치 디렉터리에 속하는지 다시 확인한 후,
그 두 PID만 종료했다. 현재 서버의 모델은 API로 메모리에서 내리고, 실제 자식 종료와
적재 모델 0개를 확인한 뒤 동일한 게이트로 재적재했다. **파일 삭제는 없다.**

- 중복 실행 당시 여유 물리 메모리: 3,451,220KiB. 정리·메모리 해제 후: 16,666,280KiB.
- 중복 실행 당시 모델 보고 크기 6,574,791,719바이트 중 VRAM은 3,119,261,941바이트였다.
  최종 모델은 6,295,440,588바이트 전부 VRAM에 적재됐고 context 8192였다.
- 서버 기록에도 복구 직후 첫 요청은 60초 후 HTTP 500으로 남았다. 중복 실행 정리와 모델
  재적재 뒤 정상 응답을 확인했다. 이 자원 경합/복구 문제를 **재시작 전 WinError 10054의
  근본 원인**이라고 주장하지 않는다.
- 최종 일반 모드: 앱 PID 32740, 서버 PID 7624, 모델 실행 PID 5720 하나.
  이전 PID 15252·31900 종료, `OLLAMA_DEBUG` 비활성, 버전과 모델 digest 동일함을 확인했다.
  PID는 관찰 기록이지 다음 작업에서 그대로 종료할 대상이 아니다.
- 상세 로그에는 AMD 드라이버 호환성 경고 1개가 있었지만 GPU 적재 자체는 확인됐다.
  이 경고가 연결 재설정 원인이라는 근거는 없으며, 로그의 업데이트 안내를 실행하지 않았다.

향후 재시작은 가능한 정상 종료 경로를 사용하고, **해당 서버의 자식 프로세스까지 종료된
것을 확인한 후** 모델을 다시 적재한다. 이름만 일치하는 모든 프로세스를 일괄 종료하지 않는다.
