## 실제 431MB 문서: 읽기 전용 재생

기존 `large-1`: 431,634,439 bytes / 1,060쪽 / 활성 청크 16,239개 / revision 17.
질문은 “심부전의 정의를 설명하는 원문 한 문장과 출처를 보여주세요.”로 유지했다.
사용자 SQLite는 `mode=ro` / `query_only=ON`, 기존 로컬 Ollama만 사용했다.
검색 → 스트리밍 공급자 → claim 검증의 탐색 재생이며 GUI·이력 저장 경로는 아니다.

- 프롬프트만 보강한 탐색 3회는 모두 보류였다. 모델은 121자 인용에 시작·중간 ID만
  붙여 끝 조각을 누락했다. 지시문 추가만으로 출처 누락이 해결되지 않았다.
- 분절 출처 복원 구현 후 3회 모두 completed, 121자 원문에 138쪽 출처 3개가 연결됐다.
  4.750 / 3.360 / 3.426초. 이는 `308edef`로 커밋한 제품 코드의 작업 트리 재생이다.
- 두 수정 적용 후에도 **3/3 completed**, 121자 원문·138쪽 출처 3개였다.
  4.766 / 3.353 / 3.371초, 검색 32청크 / 2,090자다.
  이는 `3dd178b`로 커밋한 제품 코드의 작업 트리 재생이다. 성능 벤치마크가 아니다.
- JSON의 `claim_diagnostics`는 **복원 전 모델이 낸 ID 2개** 기준이므로
  `polarity_consistent=false`가 남는다. 최종 `claims`는 누락 조각을 포함한 ID 3개로
  기존 검증을 통과한 결과다. 거부된 원래 ID 2개를 그대로 승인한 것이 아니다.
  각 실행에서 모델 원문과 승인된 claim의 SHA-256은 같다.
- 모델 전후 digest는 모두
  `sha256:500a1f067a9f782620b40bee6f7b0c89e17ae61f686b92c24933e4ca4b2b8b41`이다.
  초기 별도 원문 확인 진단의 native error frame 1회는 기존 재시도로 복구됐다.
  이 탐색을 전체 모델 안정성 또는 새 설치본 통과로 해석하지 않는다.
- [단계별 익명 재생·보존 JSON](windows-pr7-fragment-qa-20260910.json).
  사용자 원문·답변 본문·파일명·개인 경로·내부 ID·화면은 공개 증거에서 제외했다.
