## 연결 오류에서 확인한 것과 확인하지 못한 것

최초 두 중단은 선택 단계의 `SummaryNetworkError / connect_failed`다. 단독 사례 진단은
성공했지만 전체 재검사에서 다른 사례도 중단되어 원문 한 사례만의 실패로 볼 수 없었다.
세 번째 전체 실행에는 임시 진단 래퍼를 사용해 예외 종류·OS 번호·함수/파일명만 계측했다.
실제 모델 원문·예외 산문·전체 경로를 출력하지 않고 기존 선택기와 게이트를 그대로 호출했다.

- 원인 예외는 `ConnectionResetError`, `errno=10054`, `winerror=10054`였다.
- `endpoint._read_capped`의 `opener.open` → `getresponse` → `_read_status`에서 발생했다.
  **HTTP 응답 헤더를 받기 전 연결 재설정**으로 좁혔다. 모델이 잘못된 JSON을 반환한 실패가 아니다.
- Ollama 0.34.0, 리스너 `127.0.0.1:11434`, 서버 PID 25400을 확인했다.
  `/api/version`·`/api/ps` 조회가 정상이며 적재 모델 digest도 같았다. 프로세스 재시작은 하지 않았다.
- 최근 서버 로그 200줄에서 오류 패턴(`level=error`, panic, fatal, connection reset) 0줄,
  `/api/chat` 접근 기록 10줄은 HTTP 200이었다. 이는 클라이언트가 응답을 끝까지 받았다는
  증거가 아니다. 서버·전송·로컬 보안 계층 중 재설정 발생 주체와 근본 원인은 미확정이다.
- 앞선 두 중단도 같은 OS 원인이라고 단정하지 않는다. 성공한 단독 진단이나 서버 200으로
  간헐 실패를 덮지 않으며 자동 재시도·보안 설정 변경·Ollama 삭제/재설치를 하지 않았다.

## 재현과 자동 검증

API 디렉터리에서 각 명령을 별도로 실행한다. `--local`은 필수다.

```powershell
.venv/Scripts/python.exe -X utf8 scripts/evaluate_source_selection.py --local --repeat 3 --timeout 60 --strategy baseline
.venv/Scripts/python.exe -X utf8 scripts/evaluate_source_selection.py --local --repeat 3 --timeout 60 --strategy factual_axes
.venv/Scripts/python.exe -X utf8 scripts/evaluate_source_selection.py --local --repeat 3 --timeout 60 --strategy fact_checklist
```

- 실행기 JSON은 `schema_version=2`로 올리고 `strategy`를 추가했다. 종료 0/2/3의 의미는
  그대로이며 미완료나 단독 성공을 통과로 취급하는 옵션은 없다. 기본 실행은 이전 대조군이다.
- 새 회귀 **65개**, 관련 최종 **167 passed**, 0.74초. 전체 API **1,858 passed / 4 skipped**,
  126.45초, 기존 Starlette/httpx 경고 1개. 전체 검사 후 새 테스트의 잘못된 값 입력이
  단순 개수 불일치가 아닌 내부 값 검사에 도달하도록 보강하고 해당 167개를 재검사했다.
- 전체 Ruff, mypy 앱+실행기 **137개 소스** 통과. 접근 불가 기존 캐시 디렉터리의 Ruff 경고는
  남겼고 삭제·권한 변경은 하지 않았다. `git diff --check` 통과.
- 신규 테스트 함수 두 줄의 길이 오류를 먼저 고친 뒤 재검사했다. 셀프 리뷰에서 기본 전략의
  전송 동등성, 독립 정답표 미전달, 후보의 전체 묶음 보존·엄격한 파싱·중단 가드를 대조했다.
- AI 회귀 검증 스킬에 따라 고정 정답표를 유지한 채 방식 간 계약을 검사했다. 디버깅 스킬에
  따라 연결 오류 후 기능 확장을 멈추고 최소 재현과 OS 오류 계측을 기록했다.
