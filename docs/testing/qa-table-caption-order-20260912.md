## 원인과 이번 변경

2단 판정에서 짧은 표 제목이 왼쪽 열로 분류되고, 전폭 블록의 하단만 band 경계로
사용됐다. 이전 표의 오른쪽 셀보다 다음 표 제목·첫 행이 먼저 읽혀 서로 다른 표가
섞였다. 원문과 좌표는 남아 있었으며 해당 두 표는 구조화된 DocumentTable이 없었다.

`reading_order.py`에서만 제품 동작을 바꾼다. 번호가 있는 한국어/영어 표 제목이
본문 좌측에 정렬되고, 가까운 전폭 행과 모순 없는 좌표가 있을 때만 제목 위쪽을
추가 경계로 사용한다. 기존 구간 내부의 열 순서는 유지한다. 세부 기준은
[읽기 순서 문서](../pdf/reading-order.md)에 명시했다.

- 텍스트·bbox·block_index를 그대로 두고 reading_order만 보정한다.
- 보정으로 순서가 바뀌면 신뢰도를 0.5 이하로 유지한다. 표 구조가 복원됐다는 뜻이 아니다.
- 일반 절 제목을 모두 경계로 승격하거나 표 셀을 임의로 한 문장으로 합치지 않는다.
- Q&A 모델·프롬프트·검색 상한·근거 검증·평가 게이트·평가용 선택 모듈은 변경하지 않는다.
- 기존 데이터의 자동 재추출/청크 재생성·스키마 변경·설치·다운로드는 없다.

## 실제 좌표의 읽기 전용 재계산

같은 대형 문서의 관련 두 페이지, 총 79개 저장 블록을 SELECT로 읽었다.
DB는 `mode=ro`, `query_only=ON`으로 열었다. 원문·파일명·내부 ID는 공개하지 않는다.

| 확인 항목 | 수정 전 저장 순서 | 새 코드의 메모리 내 순서 |
|---|---|---|
| 표 제목과 I–IV 네 행 연속성 | 끊김 | 연속 |
| 해당 페이지를 단독 구성한 제목 청크에 네 행 포함 | 아니오 | 예 |
| 제목 청크에 이전 표 셀 혼입 | 없음 | 없음 |
| 원문·출처 좌표 | 기준 | 동일 |
| 읽기 순서 신뢰도 | 0.5 | 0.5 |
| 인접 페이지의 일반 번호 절 경계 | 잘못된 순서 | 그대로 남음 |

청크 비교는 해당 페이지 하나로 새 초안을 만든 결과이며, 전체 문서의 활성 세대나
실제 검색 32청크를 재생성한 결과가 아니다. 제목 청크 밖의 표 행/열 해석, 제목과
떨어진 조건의 연결, 최종 답변의 분류 완결성까지 검증한 것으로 해석하면 안 된다.

최초 비공개 재계산 helper는 DB의 대문자 block_type을 엔진의 소문자 타입으로
변환하지 않아 텍스트가 없는 경로로 들어갔다. 이 결과는 폐기하고 타입을 정규화한 뒤
텍스트 존재와 2단 판정을 assert하여 다시 계산했다. 위 표는 정정된 실행만 사용한다.

사용자 문서 12건·페이지 4,339건·블록 364,819건·설정 1건과 Q&A 21/104/205행의
작업 전후 해시가 모두 같다. quick_check 정상, FK 위반/활성 Q&A 0건이다.
고정 전체 모델 평가 39회, 새 설치본 GUI, 전체 Windows 검증은 이번에 수행하지 않았다.
